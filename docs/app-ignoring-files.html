Appendix C — Ignoring files

In Chapter 2, we briefly mentioned that you can instruct Git to ignore certain files. In this appendix, we will explore this topic in more detail while keeping the explanations simple and relevant to beginners.

When working with Git, you may not want to track changes to all files in your project. For example, your project might contain large files or files specific to your local environment that do not need to be shared with collaborators. You can tell Git which files to ignore by specifying patterns in a text file named .gitignore, usually placed at the root of the repository. It is often a good idea to create this file when initializing a repository to avoid accidentally committing files you do not wish to track.

Git applies the patterns in .gitignore as soon as the file is created or modified, even if it has not been staged or committed. However, .gitignore only affects untracked files. If a file is already tracked by Git, adding it to .gitignore will not stop Git from tracking it. Although committing .gitignore is not necessary for its patterns to take effect, doing so ensures that the same ignore rules are available to others working with the repository.

C.1 What files should be ignored?

A useful rule of thumb is to track files that define the project and to ignore files that are generated by the project and can easily be recreated, as well as files specific to your local environment. Small datasets that are difficult or time-consuming to reproduce may instead be worth tracking. The table below shows common categories of files that you might want to ignore:

Category Examples Reason for ignoring
Temporary files *.tmp, *.bak Temporary files created by applications.
Operating system files .DS_Store, Thumbs.db Files automatically generated by the operating system.
Editor and IDE files .Rproj.user/, *.swp Local editor settings and temporary files.
Build artifacts *.exe Generated files that can be recreated from source code.
Data raw/, data/ Large external datasets and generated data that can easily be reproduced.
Generated results output/, results/ Generated results that can easily be reproduced.

Git is particularly well suited to tracking changes in text-based files, such as source code and documentation. Although Git can also track large datasets and large binary files, doing so can substantially increase the size of a repository. This is because Git generally retains earlier versions of committed files, even when they are subsequently modified or deleted. Large files can therefore make repositories slower to work with.

C.2 Ignore patterns

A .gitignore file is a plain text file containing patterns that tell Git which files and directories to ignore. Each line can contain an ignore pattern or a comment. Git compares the names and paths of untracked files against these patterns to determine whether they should be ignored.

The patterns use a form of wildcard matching known as glob patterns. These allow you to match multiple files using a single pattern. For example, the pattern *.pdf matches all files with the .pdf extension, regardless of the rest of their names.

The table below shows some commonly used patterns and how they work. The examples assume that the .gitignore file is located at the root of the repository.

Pattern Description
file.txt Matches files named file.txt anywhere in the repository.
/file.txt Matches file.txt only at the root of the repository.
*.pdf Matches files ending in .pdf anywhere in the repository.
data/file.txt Matches file.txt in the data/ directory at the root of the repository.
data/*.txt Matches .txt files directly inside the root data/ directory, but not in its subdirectories.
data/ Matches directories named data anywhere in the repository, including their contents.
file?.txt Matches names such as file1.txt and fileA.txt, but not file12.txt.
file[1-3].txt Matches file1.txt, file2.txt, and file3.txt.

The most important wildcard characters are *, which matches zero or more characters, and ?, which matches exactly one character. Neither matches a directory separator (/). Square brackets ([]) can be used to match a single character from a specified set or range.

The forward slash / is used to separate directories in paths, even when working on Windows. A slash at the beginning of a pattern restricts it to the root of the repository, while a slash at the end indicates that the pattern matches directories rather than ordinary files.

A .gitignore file can also contain comments and blank lines. Lines beginning with # are comments, while blank lines can be used to improve readability.

There are additional rules for writing ignore patterns, but those described here cover most common situations. For a complete description, see the Git documentation on gitignore.

D Exercises

D.1 Exercise 1 - Using a .gitignore file in a project

Imagine you are a researcher who has to clean and analyse a large dataset using the R programming language.

1. Set up the project directory structure.

First, prepare the directory structure for the project. A diagram depicting the structure is shown below. For each file shown in the diagram, create an empty file with the specified name.

~/ex01-ignoring-files/
├── README.txt
├── data/
│   └── large-dataset.rds
├── output/
└── scripts/
NoteSolution

You can create the necessary directories and files using the following commands:

$ mkdir ~/ex01-ignoring-files
$ cd ex01-ignoring-files
$ mkdir data output scripts
$ touch README.txt data/large-dataset.rds

2. Create a .gitignore file.

Your initial plan is that you want to ignore large-dataset.rds because it is a large input dataset that will not be modified during the project. You also plan to save the results of your analyses as .pdf files in output/. These are generated from the source code, so you also want to ignore any .pdf files in output/.

Create a .gitignore file in the root of ex01-ignoring-files that ignores the following files:

  • data/large-dataset.rds

  • All .pdf files in output/.

NoteSolution

You can create the .gitignore file shown below with the following commands:

user-id@computer-id MINGW64 ~/ex01-ignoring-files
$ echo "data/large-dataset.rds" >> .gitignore
$ echo "output/*.pdf" >> .gitignore
$ cat .gitignore
data/large-dataset.rds
output/*.pdf
.gitignore
data/large-dataset.rds
output/*.pdf

3. Initialize repository and add files.

Now that you have set up the project structure, initialize a Git repository in ex01-ignoring-files. Afterwards, run git status to see the states of files in the working tree. Before running the command, predict which files will appear as untracked and which will not appear in its output. Finally, add all changes to the staging area and make an initial commit.

NoteSolution 
$ git init
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add ..." to include in what will be committed)
        .gitignore
        README.txt

nothing added to commit but untracked files present (use "git add" to track)

$ git add .
$ git commit -m"Initial commit"

The files .gitignore and README.txt show up as untracked. The dataset data/large-dataset.rds does not show up because its path matches a pattern in .gitignore. Note that the empty directories output/ and scripts/ do not appear in the git status output, because Git does not track empty directories. Notice that .gitignore itself appears as an untracked file, even though its patterns are already being applied by Git.

4. Work on project.

After the initial set up, you start to work on the project. For each of the following files, add an empty file with the specified name:

  • scripts/clean-data.R: Script that cleans large-dataset.rds.

  • scripts/analyses.R: Script that performs the analyses.

  • data/clean-data.rds: Cleaned dataset generated from large-dataset.rds.

  • output/analyses.pdf: Analysis results.

Afterwards, run git status -u to see the status of the files. The -u flag ensures that Git lists individual untracked files rather than grouping them by directory. Before running the command, predict which files will appear as untracked and which will be ignored. Finally, add all changes to the staging area and make another commit.

NoteSolution 
$ touch scripts/clean-data.R scripts/analyses.R
$ touch data/clean-data.rds output/analyses.pdf
$ git status -u
On branch main
Untracked files:
  (use "git add ..." to include in what will be committed)
        data/clean-data.rds
        scripts/analyses.R
        scripts/clean-data.R

nothing added to commit but untracked files present (use "git add" to track)

$ git add .
$ git commit -m"Clean data and run analyses"

The files data/clean-data.rds, scripts/analyses.R, and scripts/clean-data.R appear as untracked files, but output/analyses.pdf does not, because the name matches a pattern in .gitignore.

If you have already committed a file, adding it to .gitignore will not stop Git from tracking it. To stop tracking a file without deleting it from your working tree, you can use git rm --cached followed by the path to the file. This stages the removal of the file from Git’s tracked contents while keeping it in your working tree. Once the removal is committed, Git will no longer track the file.

5. Stop tracking a file.

At this point you realise that you have committed data/clean-data.rds and are tracking changes to it. Since this dataset is also quite large and can easily be recreated using scripts/clean-data.R, you decide that Git should no longer track the file.

  • Stop tracking data/clean-data.rds without deleting it from the working tree.

  • Update .gitignore to ignore all .rds files in data/.

  • Add all changes to the staging area.

  • Run git status to see the status of files.

  • Commit the changes.

NoteSolution 
$ git rm --cached data/clean-data.rds
$ echo "data/*.rds" >> .gitignore
$ git add .
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        modified:   .gitignore
        deleted:    data/clean-data.rds


$ git commit -m"Stop tracking clean-data.rds"

Notice that data/clean-data.rds is shown as deleted, even though the file still exists in the working tree. This is because Git is preparing to record the file’s removal in the next commit, rather than deleting it from your computer.

Notice that data/*.rds also matches data/large-dataset.rds, so the earlier pattern is now redundant.

6. Consider whether data/clean-data.rds is still in the repository.

You have stopped tracking data/clean-data.rds, but does the file still exist in the repository’s history?

NoteSolution

Yes, data/clean-data.rds is still in the repository. Although Git no longer tracks the file in the current version, it remains available in earlier commits.
