4  Comparing versions of files

Git allows us to compare different versions of files, whether they are in the working tree, the staging area, or different commits. In this chapter, we will learn how to use the git diff command to make these comparisons and how to interpret the differences it displays.

4.1 Compare the working tree and the staging area

Using git diff with no arguments will show changes in the working tree that are not in the staging area. This allows us to inspect changes to tracked files before adding them to the staging area using git add ..

Let’s illustrate this with an example. First, we initialize a new Git repository and create a file in the working tree:

$ mkdir ~/example01-git-diff
$ cd ~/example01-git-diff
$ git init
$ echo "Contents of file1.txt" > file1.txt

Now let’s run git diff:

$ git diff

Notice that git diff produces no output. This is because file1.txt is an untracked file at this point, and the staging area is empty, so there is nothing for git diff to compare. Let’s add file1.txt to the staging area and commit the file, then make additional changes in the working tree and run git diff again:

$ git add file1.txt
$ git commit -m "Add file1.txt"
$ echo "New content in working tree" >> file1.txt
$ git diff
diff --git a/file1.txt b/file1.txt
index 85e8799..ebfc449 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1,2 @@
 Contents of file1.txt
+New content in working tree

git diff now shows us the changes in the working tree relative to the staging area. In this example, it shows that we have added the line “New content in the working tree” to file1.txt.

4.2 Understanding the diff output

As you saw in the example in the previous section, the output from git diff contains several elements worth explaining. We will use the preceding example to explain the different parts of the output.

Structure of git diff output

For each file being compared, Git displays a separate section of the diff output, beginning with a file header that identifies the file. Within each file section, Git groups changes into one or more hunks, which are sections of the file containing changes and surrounding unchanged lines. Each hunk begins with a hunk header.

In our simple example, only one file has been modified, and its changes are contained in a single hunk.

The file header

The first line of each file section is called the file header:

diff --git a/file1.txt b/file1.txt

The file header identifies the two versions of the file being compared. Git uses the prefixes a/ and b/ to distinguish them. These prefixes do not indicate actual directories, but represent the original and modified versions of the file, respectively.

In our example, where we use git diff without arguments, a/file1.txt refers to the version in the staging area, while b/file1.txt refers to the version in the working tree.

The prefix diff --git might suggest that Git has executed the Bash command diff with a --git option, but this is not the case. Instead, diff --git is part of the output format generated by Git.

File metadata

The second line

index 85e8799..ebfc449 100644

displays some Git metadata. We will not examine this metadata in detail, but simply note that 85e8799 and ebfc449 are abbreviated object IDs identifying the two versions of the file being compared. In addition to the index line, Git may display other metadata, such as new file mode 100644 when a file has been added or deleted file mode 100644 when a file has been deleted.

Markers for changes

The next two lines establish which symbols are associated with each version of the file:

--- a/file1.txt
+++ b/file1.txt

The --- line associates the - symbol with the original version of the file (a/file1.txt), while the +++ line associates the + symbol with the modified version (b/file1.txt). These symbols are used in the diff content to indicate which lines are present in one version but not the other.

The hunk header

The next line

@@ -1 +1,2 @@

is called the hunk header. It identifies the line ranges shown in the hunk for each of the two versions being compared.

The part beginning with - refers to the original version of the file, while the part beginning with + refers to the modified version as established by the markers explained above. Each part contains the starting line number followed by the number of lines shown, separated by a comma.

In our example, -1 indicates that the hunk contains one line from the original version, starting at line 1. Similarly, +1,2 indicates that the hunk contains two lines from the modified version, starting at line 1.

When only one line is shown, the number of lines is omitted, as in -1.

A file may contain multiple hunks, each with its own hunk header. We will see an example of this later in the chapter.

The diff content

The remaining output

 Contents of file1.txt
+New content in working tree

contains the diff content, which consists of individual diff lines that can be divided into three types:

  • Context lines: Lines that have not changed between the two versions. These lines help you understand where in the file changes are happening. By default, these lines are shown in grey. In our example, the Contents of file1.txt line is a context line, since it is present in both versions of the file. These lines are preceded by a space rather than a + or -.

  • Deletion lines: Lines that were present in the original version, but are not present in the modified version. These lines are preceded by a -. By default, these lines are shown in red. Our current example does not contain any deletion lines.

  • Addition lines: Lines that are present in the modified version, but were not present in the original version. These lines are preceded by a +. By default, these lines are shown in green. In our example, New content in working tree is an addition line.

Together, these lines show how the file differs between two versions. When an existing line is modified, Git typically represents the change as a deletion of the original line followed by an addition of the modified line. The surrounding context lines help us understand where the changes occur in the file.

General structure of diff output

The following schematic summarizes how Git organizes diff output into file sections and hunks. When differences are found, the output consists of one or more file sections, each beginning with a file header and associated metadata. Within each file section, changes are grouped into one or more hunks, each beginning with a hunk header followed by the lines showing the changes. The number of file sections and hunks depends on the files being compared and the changes made to them.

File section 1
File header and metadata
diff --git, index, ---, +++
Hunk 1
@@ ... @@ followed by diff lines
...
Hunk m
@@ ... @@ followed by diff lines
...
File section n
File header and metadata
diff --git, index, ---, +++
Hunk 1
@@ ... @@ followed by diff lines
...
Hunk m
@@ ... @@ followed by diff lines

4.3 Understanding diff output with changes to multiple files

Now that we can interpret the output of git diff, let’s look at a slightly more realistic example of a diff with changes to multiple files. First, we create a repository containing two files, commit them, and then modify both files:

$ mkdir ~/example02-git-diff
$ cd ~/example02-git-diff
$ git init
$ touch file1.txt
$ touch file2.txt
$ git add .
$ git commit -m "Add file1.txt and file2.txt"
$ echo "Contents of file1.txt" >> file1.txt
$ echo "Contents of file2.txt" >> file2.txt

Next, we run git diff:

$ git diff
diff --git a/file1.txt b/file1.txt
index e69de29..85e8799 100644
--- a/file1.txt
+++ b/file1.txt
@@ -0,0 +1 @@
+Contents of file1.txt
diff --git a/file2.txt b/file2.txt
index e69de29..92e49c3 100644
--- a/file2.txt
+++ b/file2.txt
@@ -0,0 +1 @@
+Contents of file2.txt

Notice that the output contains two separate file sections, one for file1.txt and another for file2.txt. Each section begins with a file header (diff --git) identifying the file being compared, followed by metadata and the changes to that file. In this example, each file section contains a single hunk, identified by its hunk header (@@ ... @@).

4.4 Understanding diff output with multiple changes to a file

When a file contains multiple changes, and these changes are not near each other, Git may divide the changes into multiple hunks rather than displaying the entire file, with a few context lines around each change. Let’s illustrate this using the Bash command seq to create a file with 20 numbered lines. We then use sed to modify its first and last lines of the file. You do not need to understand the syntax of these commands; they are used only to prepare the example.

First, we create a repository where we create and commit the file, then modify its first and last lines:

$ mkdir ~/example03-git-diff
$ cd ~/example03-git-diff
$ git init
$ seq 1 20 > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"
$ sed -i '1s/.*/Modified first line/' file1.txt
$ sed -i '$s/.*/Modified last line/' file1.txt

Next, we execute git diff:

$ git diff
diff --git a/file1.txt b/file1.txt
index 0ff3bbb..b5ad34d 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1,4 +1,4 @@
-1
+Modified first line
 2
 3
 4
@@ -17,4 +17,4 @@
 17
 18
 19
-20
+Modified last line

Notice that the diff contains two hunks because the changes occur in different parts of the file. Each hunk has its own hunk header, indicating which lines from the original and modified versions are shown. The first hunk shows a change to line 1, while the second shows a change to line 20. Each hunk also contains a few surrounding context lines.

4.5 Compare the staging area with the current commit

To compare the staging area with the current commit (HEAD), we can use git diff --staged. This will show us the changes that have been added using git add and would be included in the next commit if git commit were executed. When the repository has no commits, Git compares the staging area with an empty version of the repository containing no files.

In Git, HEAD is a special reference that identifies the current commit. We can use HEAD to refer to this commit without having to specify its commit ID. Git references, including HEAD, are explained in more detail in Appendix D.

Let’s illustrate this with a new example. First, we create a repository and stage a new file:

$ mkdir ~/example04-git-diff
$ cd ~/example04-git-diff
$ git init
$ echo "Original content" > file1.txt
$ git add file1.txt

We can now execute git diff --staged to see the changes we have staged:

$ git diff --staged
diff --git a/file1.txt b/file1.txt
new file mode 100644
index 0000000..3b94cd9
--- /dev/null
+++ b/file1.txt
@@ -0,0 +1 @@
+Original content

Notice the /dev/null output in the markers. The marker --- /dev/null indicates that the file does not exist in the original version being compared.

Next, we commit the staged changes, modify the file, stage the modification, and run git diff --staged again:

$ git commit -m "Add file1.txt"
$ echo "Change original content" > file1.txt
$ git add .
$ git diff --staged
diff --git a/file1.txt b/file1.txt
index 3b94cd9..74e17e4 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1 @@
-Original content
+Change original content

Notice that Git represents the modified line as a deletion of the original line followed by an addition of the new line. The original line Original content is present in HEAD but has been replaced in the staging area.

4.6 Compare the working tree with the current commit

Sometimes it is useful to see all differences between the current commit and the working tree, regardless of whether they have been staged or not. To do this we can use git diff HEAD, which compares HEAD (the current commit) with the working tree.

Consider the following example, where we first create file1.txt containing a single line and commit it. Next, we add another line and stage that change. Finally, we add a third line in the working tree that is not staged:

$ mkdir ~/example05-git-diff
$ cd ~/example05-git-diff
$ git init
$ echo "Line 1" > file1.txt
$ git add .
$ git commit -m "Add file1.txt"
$ echo "Line 2" >> file1.txt
$ git add file1.txt
$ echo "Line 3" >> file1.txt

Running git diff at this point would show only the unstaged change of adding the third line, and using git diff --staged would only show us the staged change of adding the second line. However, running git diff HEAD shows both changes:

$ git diff HEAD
diff --git a/file1.txt b/file1.txt
index 3be9c81..6ad36e5 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1,3 @@
 Line 1
+Line 2
+Line 3

4.7 Compare two commits

We can use the form git diff <commit1> <commit2> to compare two different commits.

First, let’s create a new repository with three commits:

$ mkdir ~/example06-git-diff
$ cd ~/example06-git-diff
$ git init
$ echo "Line added in first commit" > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"
$ echo "Line added in second commit" >> file1.txt
$ git add file1.txt
$ git commit -m "Add line to file1.txt"
$ echo "Completely change contents in third commit" > file1.txt
$ git add file1.txt
$ git commit -m "Completely change content of file1.txt"

As we have already seen, HEAD refers to the current commit. We can also use HEAD^ to refer to the first parent of the commit identified by HEAD. We can therefore use git diff HEAD^ HEAD to show the changes introduced in the current commit:

$ git diff HEAD^ HEAD
diff --git a/file1.txt b/file1.txt
index cecb547..9dc41f3 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1,2 +1 @@
-Line added in first commit
-Line added in second commit
+Completely change contents in third commit

We can also use git log --oneline to find the abbreviated commit IDs of the commits in the repository, then use these to compare the first and third commits:

$ git log --oneline
1fdab67 (HEAD -> main) Completely change content of file1.txt
d481959 Add line to file1.txt
a41cc0a Add file1.txt
$ git diff a41cc0a 1fdab67
diff --git a/file1.txt b/file1.txt
index 67b6d9e..9dc41f3 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1 @@
-Line added in first commit
+Completely change contents in third commit

4.8 Comparing individual files

By default, git diff shows differences for all tracked files that have changed between the versions being compared. However, we can also restrict the comparison to individual files.

For example, to show only unstaged changes to file1.txt, we can use:

$ git diff -- file1.txt

The -- separates the filename from the other arguments passed to git diff. This tells Git that file1.txt is a file whose changes we want to inspect.

We can also specify a filename when using other forms of git diff:

$ git diff --staged -- file1.txt
$ git diff HEAD -- file1.txt
$ git diff HEAD^ HEAD -- file1.txt

These commands perform the same comparisons introduced earlier in the chapter, but restrict the output to changes involving file1.txt.

We can also specify multiple filenames to compare only the selected files:

$ git diff -- file1.txt file2.txt

4.9 Summary

In this chapter, we have learned how to use git diff to compare different states of a Git repository and how to interpret the output it produces. A diff shows the differences between two versions of a file, including added and deleted lines, as well as modified lines represented by deletions and additions. It also shows unchanged lines surrounding the changes to provide context. Understanding this output is useful not only when using git diff, but also when using other Git commands that display diffs, such as git show.

We have introduced several ways to use git diff to compare different states of a repository:

Command Comparison
git diff Staging area → Working tree
git diff --staged HEAD → Staging area
git diff HEAD HEAD → Working tree
git diff HEAD^ HEAD Parent of HEAD → HEAD
git diff <commit1> <commit2> First commit → Second commit

Remember that the order of the versions being compared matters when using git diff <commit1> <commit2>. Changes are presented as additions or deletions relative to the first version, so reversing the order of the versions being compared causes additions to appear as deletions and vice versa.

Exercise 3 - Understanding the direction of comparisons

In this exercise, we will explore how the order of commits specified when using git diff affects the output. Remember that git diff compares two versions of a file, treating the first as the original version and the second as the modified version.

First, create a Git repository with two commits containing different versions of a file named article.txt:

$ mkdir ~/ex03-git-diff
$ cd ~/ex03-git-diff
$ git init
$ echo "Introduction" > article.txt
$ echo "Methods" >> article.txt
$ echo "Results" >> article.txt
$ git add article.txt
$ git commit -m "Add article draft"
$ # Recreate the article draft from scratch
$ echo "Introduction" > article.txt
$ echo "Methods" >> article.txt
$ echo "Discussion" >> article.txt
$ git add article.txt
$ git commit -m "Revise article draft"

1. Compare the first commit with the second commit.

Use git diff HEAD^ HEAD to compare the first commit with the second commit.

Before running the command, consider the following questions:

  • Which commit is treated as the original version, and which is treated as the modified version?

  • Which lines do you expect to be displayed as additions and deletions?

NoteSolution 
$ git diff HEAD^ HEAD
diff --git a/article.txt b/article.txt
index 8353619..a5d5ce8 100644
--- a/article.txt
+++ b/article.txt
@@ -1,3 +1,3 @@
 Introduction
 Methods
-Results
+Discussion

The first commit (HEAD^) is treated as the original version, while the second commit (HEAD) is treated as the modified version.

The line Results appears as a deletion because it was present in the first commit but not in the second. The line Discussion appears as an addition because it is present in the second commit but not in the first.

2. Reverse the order of the commits.

Now use git diff HEAD HEAD^ to reverse the order of the commits being compared.

Before running the command, predict how the output will differ from the previous comparison.

NoteSolution 
$ git diff HEAD HEAD^
diff --git a/article.txt b/article.txt
index a5d5ce8..8353619 100644
--- a/article.txt
+++ b/article.txt
@@ -1,3 +1,3 @@
 Introduction
 Methods
-Discussion
+Results

The same two versions of the file are being compared, but their order has been reversed. The second commit (HEAD) is now treated as the original version, while the first commit (HEAD^) is treated as the modified version.

Consequently, Discussion is displayed as a deletion, while Results is displayed as an addition.

Notice that reversing the order of the commits reverses the additions and deletions, even though the contents of the two commits have not changed.

3. Interpreting a reverse comparison.

Imagine that you have discovered a problem with the changes introduced in the second commit and are considering restoring article.txt to its state in the first commit.

Which of the two comparisons would be more useful for understanding the changes needed to restore the earlier version? Explain your answer.

NoteSolution

The reverse comparison, git diff HEAD HEAD^, shows the differences between the current version and the earlier version, treating the earlier version as the desired result.

In our example, it shows that restoring the earlier version would involve replacing Discussion with Results.

Remember that git diff only displays differences between versions of files. It does not modify files or undo commits.
