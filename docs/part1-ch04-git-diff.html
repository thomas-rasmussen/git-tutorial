4  Understanding Git diffs

Some Git commands, in particular, git diff can be used to compare different states of a Git repository. In this chapter we will introduce the git diff command, learn how to interpret the output it produces, and show how it can be used to compare versions of files.

4.1 Compare the working tree and the staging area

Using git diff with no arguments will show changes in the working tree that are not in the staging area. This invocation of git diff can be used to see what changes would be added to the staging area if we ran git add ..

Let’s illustrate this with an example. First, we initialize a Git repository in an empty directory, and create a file in the working tree:

$ mkdir ~/example01-git-diff
$ cd ~/example01-git-diff
$ git init
$ echo "Contents of file1.txt" > file1.txt

Now let’s we run git diff:

$ git diff

Notice that git diff produces no output. This is because file1.txt is an untracked file at this point, and the staging area is empty, so there is nothing for git diff to compare. Let’s add file1.txt to the staging area and commit the file, then we add new changes in the working tree and run git diff again:

$ git add file1.txt
$ git commit -m"Add file1.txt"
$ echo "New content in working tree" >> file1.txt
$ git diff
diff --git a/file1.txt b/file1.txt
index 85e8799..4527427 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1,2 @@
 Contents of file1.txt
+New content in working tree

git diff now shows us the changes in the working tree as compared to the staging area, namely that we have added the line “New content in the working tree” to file1.txt.

4.2 Understanding the diff output

As you saw in the example in the previous section, the output from git diff is quite technical and requires some explanation. We will do this based on the git diff output from the example.

Structure of git diff output

For each file being compared, Git displays a separate section of the diff output, beginning with a file header that identifies the file. Within each file section, Git groups changes into one or more hunks, which are sections of the file containing changes and surrounding unchanged lines. Each hunk begins with a hunk header.

In our simple example, only one file has been modified, and its changes are contained in a single hunk.

The file header

The first line of each file sectin is called the file header:

diff --git a/file1.txt b/file1.txt

The file header identifies the file being compared and indicates that Git is comparing two versions of that file. It is informing us what inputs has been given to the diff. We can see that two versions of file1.txt has been passed to the diff, a/file1.txt and b/file1.txt. It looks like Git is comparing two files with the file paths a/file1.txt and b/file1.txt, which is not the case. Git is just informing us, in a somewhat confusing way, that the first input has been assigned the symbol “a” and the second input has been assigned the symbol “b”. In this example where we have called git diff with no arguments, the first input “a” is the version of file1.txt in the staging area, and “b” is the version of file1.txt in the working tree. You can think of version “a” as the “old” or “original” version of the file, and “b” as the “new” or “modified” version of the file. Again, this makes sense in our current example where we want to see the changes in the working tree not yet added to the staging area: the old version is the version in the staging area, and the new version is the version in the working tree.

The start of the line diff --git might look like that Git has run the BASH command diff with a --git flag, but this is not actually the case. This is just Git’s way of telling us that the diff has been produced by Git’s own internal diff function.

File metadata

The second line

index 85e8799..4527427 100644

displays some Git metadata. We will not concern ourselves with what this means exactly, but simply note that 85e8799 and 4527427 are abbreviated SHA-1 hashes of the content that is compared.

Markers for changes

The next lines

--- a/file1.txt
+++ b/file1.txt

are a legend that assigns symbols to diff input sources. In this case, changes from version “a” of the file is marked with a “—”, and changes from version “b” is marked with a “+++” symbol.

The hunk header

The next line

@@ -1 +1,2 @@

is called the hunk header. It identifies the line ranges shown in the hunk for each of the two versions being compared.

The part beginning with - refers to the original version of the file, while the part beginning with + refers to the modified version. Each part contains the starting line number followed by the number of lines shown, separated by a comma.

In our example, -1 indicates that the hunk contains one line from the original version, starting at line 1. Similarly, +1,2 indicates that the hunk contains two lines from the modified version, starting at line 1.

When only one line is shown, the number of lines is omitted, as in -1.

A file may contain multiple hunks, each with its own hunk header. We will see an example of this later in the chapter.

The diff content

The remaining output

 Contents of file1.txt
+New content in working tree

is the diff content, and consists of three different types of diff lines.

  • Context lines: Lines that have not changed between the two versions. These lines help you understand where in the file changes are happening. By default, these lines are shown in grey. In our example, the “Contents of file1.txt” line is a context line, since it is present in both versions of the file. These lines are not preceded by any symbol.

  • Deletion lines: Lines that were present in version “a”, the old version, but are not present in the new version, “b”. These lines are preceded by a “-”. By default, these lines are shown in red. Our current example does not contain any deletion lines.

  • Addition lines: Lines that are present in version “b”, the new version, but were not present in version “a”, the old version. These lines are preceded by a “+”. By default, these lines are shown in green. In our example, “New content in working tree” is an addition line.

The diff content essentially provides a before-and-after snapshot of parts of your file. You can see the context (what part of the file remained unchanged), the deletions (what parts were removed from the old version), and the additions (what parts were added in the new version). As indicated by the colors and symbols, you can think of the diff content as a chunk of changes in the file, with some context lines around changes to provide context, red deletion lines indicating what lines have been removed from the original file, and green addition lines showing what has been added in the modified version.

Genral structure of diff output

The general structure of a diff is illustrated below. The output consists of one or more file sections, each beginning with a file header and associated metadata. Within each file section, changes are grouped into one or more hunks, each beginning with a hunk header followed by the lines showing the changes. The number of file sections and hunks depends on the files being compared and the changes made to them.

File section 1
File header and metadata
diff --git, index, ---, +++
Hunk 1
@@ ... @@ followed by diff lines
...
Hunk m
@@ ... @@ followed by diff lines
...
File section n
File header and metadata
diff --git, index, ---, +++
Hunk 1
@@ ... @@ followed by diff lines
...
Hunk m
@@ ... @@ followed by diff lines

4.3 Understanding diff output with changes to multiple files

Now that we can interpret the output of git diff let’s look at a slightly more realistic example of a diff with changes to multiple files. First, we create a repository with two files that we commit, and then make additional changes to:

mkdir ~/example02-git-diff
$ cd ~/example02-git-diff
$ touch file1.txt
$ touch file2.txt
$ git add .
$ git commit -m"Add file1.txt and file2.txt"
$ echo "Contents of file1.txt" >> file1.txt
$ echo "Contents of file2.txt" >> file2.txt

Next we run git diff:

$ git diff
diff --git a/file1.txt b/file1.txt
index e69de29..85e8799 100644
--- a/file1.txt
+++ b/file1.txt
@@ -0,0 +1 @@
+Contents of file1.txt
diff --git a/file2.txt b/file2.txt
index e69de29..92e49c3 100644
--- a/file2.txt
+++ b/file2.txt
@@ -0,0 +1 @@
+Contents of file2.txt

Notice that the output contains two separate file sections, one for file1.txt and another for file2.txt. Each section begins with a file header (diff –git) identifying the file being compared, followed by metadata and the changes to that file. In this example, each file section contains a single hunk, identified by its hunk header (@@ … @@).

4.4 Understanding diff output with multiple changes to a file

When a file contains multiple changes, and these changes are not near each other, the diff will not show the entire file in one diff, but instead show multiple diff hunks, with a few context lines around each change. Let’s illustrate this with an example. First we create a repository with a commit of file with 20 numbered lines, then we change the first and last line:

$ mkdir ~/example03-git-diff
$ cd ~/example03-git-diff
$ git init
$ # Create a file with 20 numbered lines
$ seq 1 20 > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"
$ # Modify first and last line of file
$ sed -i '1s/.*/Modified first line/' file.txt
$ sed -i '$s/.*/Modified last line/' file.txt

Next, we execute git diff:

$ git diff
diff --git a/file1.txt b/file1.txt
index 0ff3bbb..b5ad34d 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1,4 +1,4 @@
-1
+Modified first line
 2
 3
 4
@@ -17,4 +17,4 @@
 17
 18
 19
-20
+Modified last line

Unlike the previous example, this diff contains only one file section, since only file1.txt has been modified. However, the file section contains two hunks because the changes occur in different parts of the file. Each hunk has its own hunk header, indicating which lines from the original and modified versions are shown.

Notice that the first hunk shows changes around line 1, while the second shows changes around line 17. Instead of displaying the entire file, Git separates the changes into two hunks, each containing the modified lines and a few surrounding context lines.

4.5 Compare staging area and latest commit

To compare the the staging area and the latest commit (HEAD), we can use git diff --staged. This will show us the changes that have been added using git add and would be included in the next commit if git commit were executed. This also works if there is no commits in the repository. In this case, Git compares the staging area with a repository containing no files.

In Git, HEAD is a special reference that identifies the current commit, which is normally the latest commit in the repository’s history. We can use HEAD to refer to this commit without having to specify its commit ID. Git references, including HEAD, are explained in more detail in Appendix D.

Let’s illustrate this with a new example. First we set up a repository where we create and stage a file:

$ mkdir example02-git-diff
$ cd example02-git-diff
$ git init
$ echo "Original content" > file1.txt
$ git add file1.txt

We can now execute git diff --staged to see the changed we have staged:

$ git diff --staged
diff --git a/file1.txt b/file1.txt
new file mode 100644
index 0000000..3b94cd9
--- /dev/null
+++ b/file1.txt
@@ -0,0 +1 @@
+Original content

Notice the /dev/null output in the markers. This is because this version of the file does not exist.

Next, let’s try to commit the changes, then change the line in the file, stage the changes, and run git diff --staged again:

$ git commit -m "Add file1.txt"
$ echo "Change original content" > file1.txt
$ git add .
$ git diff --staged
diff --git a/file1.txt b/file1.txt
index 3b94cd9..74e17e4 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1 @@
Original content
+Change original content

In this diff we can see that changing the line in the file, has resulted in a diff with a deletion line and an addition line. The line “Original content” is not in the version in the staging area, and the line “Change original content” has been added.

4.6 Comparing the working tree to the last commit

Sometimes it is useful to see all changes that have been made since the latest commit, regardless of whether they have been staged or not. To do this we can use git diff HEAD which compares HEAD (the previous commit) with the working tree.

Suppose we have a repository with the following history:

$ mkdir ~/example03-git-diff
$ cd ~/example03-git-diff
$ git init
$ echo "Line 1" > file1.txt
$ git add .
$ git commit -m "Add file1.txt"
$ echo "Line 2" >> file1.txt
$ git add file1.txt
$ echo "Line 3" >> file1.txt

Here, We have made a file, file1.txt with one line in it, and committed it. Next, we have added another line and staged that change, and finally we have added a third line in the working tree that is not staged. If we ran git diff at this point would only show us the unstaged change of adding the third line, and using git diff --staged would only show us the staged change of adding the second line. But if we run git diff HEAD we both changes:

$ git diff HEAD
diff --git a/file1.txt b/file1.txt
index 3be9c81..6ad36e5 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1,3 @@
 Line 1
+Line 2
+Line 3

4.7 Compare two commits

We can use the form git diff <commit-id1> <commit-id2> to compare two different commits.

First, let’s create a new repository with 3 commits:

$ mkdir ~/example04-git-diff
$ cd ~/example04-git-diff
$ git init
$ echo "Line added in first commit" > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"
$ echo "Line added in second commit" >> file1.txt
$ git add file1.txt
$ git commit -m "Add line to file1.txt"
$ echo "Completely change contents in third commit" > file1.txt
$ git add file1.txt
$ git commit -m "Completely change content of file1.txt"

Git also provides a convenient way to refer to earlier commits using HEAD. By adding ^ to HEAD, we get HEAD^, which refers to the first parent of the commit identified by HEAD. In other words, for the simple commit history in our example, HEAD^ refers to the commit immediately preceding the latest commit. We can therefore use git diff HEAD^ HEAD to show the changes introduced in the latest commit:

$ git diff HEAD^ HEAD
diff --git a/file1.txt b/file1.txt
index cecb547..c19ca71 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1,2 +1 @@
-Line added in first commit
-Line added in second commit
+Completely change file contents in third commit

We could also use git log --oneline to find the abbreviated commit IDs of each commits, then use these to compare the first and third commit:

$ git log --oneline
$ git log --oneline
1fdab67 (HEAD -> main) Completely change content of file1.txt
d481959 Add line to file1.txt
a41cc0a Add file1.txt
$ git diff a41cc0a 1fdab67
diff --git a/file1.txt b/file1.txt
index 67b6d9e..c19ca71 100644
--- a/file1.txt
+++ b/file1.txt
@@ -1 +1 @@
-Line added in first commit
+Completely change file contents in third commit

4.8 Summary

In this chapter, we have learned how to use git diff to compare different states of a Git repository and how to interpret the output it produces. A diff shows the differences between two version of a file, including lines that have been added, deleted, or modified. It also shows unchanaged lines surrounding the changes to provide context. Understanding this output is useful not only when using git diff, but also when using other Git commands that display diffs, such as git show.

We have introduced several ways to use git diff to compare different states of a repository:

Command Comparison
git diff Staging area → Working tree
git diff --staged HEAD → Staging area
git diff HEAD HEAD → Working tree
git diff HEAD^ HEAD Parent of HEAD → HEAD
git diff <commit1> <commit2> First commit → Second commit

Remember that the order of the versions being compared matters. Changes are presented as additions or deletions relative to the first version, so reversing the order of a comparison also reverses the additions and deletions shown in the diff.

Exercise 3 - Understanding the direction of comparisons

First, create a Git repository with two commits containing different verisons of a file named article.txt:

$ mkdir ~/ex03-git-diff

The first commit (HEAD^) is treated as the original version, while the second commit (HEAD) is treated as the modified version.

The line Results appears as a deletino because it was presente in the first commit but no in the second. The line Discussion appears an addition because it is present in the second commit bu not in the first.

The same two versions of the file are being compared, but their order has been reversed. The second commit (HEAD) is now treated as the original version, while the first commit (HEAD^) is treated as the modified version.

Consequently, Discussion is displayed as a deletion, while Results is displayed as an addition.

Notice that reversing the order of the commits reverses the additions and deletions, even though the contents of the two commits have not changed.

3. Interpreting a reverse comparison

Imagine that you have discovered a problem with the changes introduced in the second commit and are considering restoring article.txt to its state in the first commit.

Which of the two comparisons would be more useful for understanding the changes needed to restore the earlier version? Explain your answer.

NoteSolution

The reverse comparison, git diff HEAD HEAD^, shows the differences between the current version and the earlier version, treating the earlier version as the desired result.

In our example, it shows that restoring the earlier version would involve replacing Discussion with Results.

Remember that git diff only displays differences between versions of files. It does not modify files or undo commits.
