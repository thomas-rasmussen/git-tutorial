8  Introduction to GitHub

GitHub is a web-based service for hosting Git repositories. You can host a remote Git repository on GitHub instead of maintaining your own server or using one on a local network. This makes it easy to access your repository from different computers and share it with others. However, GitHub is much more than a service for hosting repositories. It also provides a wide range of features for collaboration and other purposes. Covering all these features would require a tutorial of its own, so this chapter will introduce and illustrate only a selection of them.

GitHub has a web user interface that is easy to navigate and is often the most convenient way to interact with GitHub. However, explaining how to use the web interface in a written tutorial would require numerous screenshots and detailed instructions. Instead, in line with the philosophy of this tutorial, we will use the GitHub CLI to interact with GitHub from the command line. This approach works well for the features introduced here, although the web interface may be more convenient for some tasks. You can find documentation on how to use GitHub, including its web interface, on the GitHub website.

It is important to understand that Git and GitHub are two different things. Git is a version control system, whereas GitHub is a web-based service for hosting Git repositories and facilitating collaboration. Similarly, the git and gh commands serve different purposes. We use git commands to perform Git operations, while we use gh commands to interact with GitHub through the GitHub CLI.

8.1 Create a GitHub account and install the GitHub CLI

To create repositories or contribute to projects on GitHub, you need a GitHub account. You can create a free account by visiting https://github.com and signing up.

To interact with GitHub from the command line, we will use the GitHub CLI. You can install it by running the following command:

$ winget install --id GitHub.cli

This should work from Git Bash. If not, try running the command in PowerShell. Alternatively, download and install it from https://cli.github.com/.

After installation, restart your terminal so that the gh command becomes available.

8.2 Authenticate with your GitHub account

Before using the GitHub CLI to create or modify repositories on GitHub, we need to authenticate with our GitHub account. This verifies our identity and allows the CLI to access our account. Git can communicate with GitHub using either HTTPS or SSH, but explaining the differences between these protocols is outside the scope of this tutorial. Here, we will use the GitHub CLI to authenticate with GitHub through a web browser and configure HTTPS as our preferred protocol for Git operations. This also allows the GitHub CLI to provide authentication credentials when pushing changes to GitHub using Git.

$ gh auth login --git-protocol https --web --clipboard

Open the URL displayed in the terminal. If you are not logged into your GitHub account already, you will be prompted to do so first. Then you will be asked to enter the one-time code displayed in the terminal (which should already have been copied to the clipboard).

Once you have completed the authentication process, verify that it succeeded using gh auth status. The output should resemble the following:

$ gh auth status
github.com
  ✓ Logged in to github.com account your-user-name (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
  - Token scopes: 'gist', 'read:org', 'repo', 'workflow'

The output may vary depending on your GitHub CLI configuration and the permissions granted to your account. In particular, the token scopes shown in the output indicate which permissions have been granted to the GitHub CLI.

After authentication, the GitHub CLI normally stores your credentials securely in Windows Credential Manager, so you do not need to authenticate every time you use GitHub. If secure credential storage is unavailable, the GitHub CLI will instead store your credentials in a plain text file.

The rest of this chapter assumes that you have created a GitHub account and authenticated using the GitHub CLI.

8.3 Creating a repository on GitHub

There are two ways to set up a repository on GitHub. You can create a new repository on GitHub and then clone it to your computer, or you can create a local repository and subsequently publish it on GitHub. Both approaches work, and which one you choose is largely a matter of preference.

We can use gh repo create to create a repository on GitHub, either from scratch or from an existing local repository. It is possible to create a repository interactively in the terminal by running gh repo create with no arguments, but that is not something we will explore here. Instead, we will create repositories non-interactively by specifying a repository name and indicating whether the repository should be public (--public) or private (--private). Public repositories can be seen by everyone. Private repositories can only be accessed by you and other people you have granted access to.

Initialize a new Git repository on GitHub

Let’s illustrate how to initialize a new Git repository directly on GitHub. We need to give the repository a name and specify whether it should be public or private. It is also common to initialize a repository with a README file:

$ gh repo create init-on-github --public --add-readme

This creates a new public repository called init-on-github in your GitHub account with an initial README.md file.

We can now clone the repository and start working on the project. Cloning automatically configures the GitHub repository as a remote:

$ cd ~
$ git clone https://github.com/your-user-name/init-on-github.git
$ cd init-on-github
$ git log --oneline
9caef1d (HEAD -> main, origin/main, origin/HEAD) Initial commit
$ ls
README.md
$ git remote -v
origin  https://github.com/your-user-name/init-on-github.git (fetch)
origin  https://github.com/your-user-name/init-on-github.git (push)

In the terminal commands above, replace your-user-name with your GitHub username.

Upload an existing local repository

Imagine that we have created the following local Git repository:

$ mkdir ~/init-local-repo
$ cd ~/init-local-repo
$ git init
$ touch README.txt
$ git add README.txt
$ git commit -m "Initial commit"

To upload the repository to GitHub, we use gh repo create with the --source option to specify the local repository. We can use --push to push the local commits to GitHub and --remote to specify the name for the remote:

$ gh repo create init-local-repo --public --source=. --remote=origin --push
$ git log --oneline
f662630 (HEAD -> main, origin/main) Initial commit
$ git remote -v
origin  https://github.com/your-user-name/init-local-repo (fetch)
origin  https://github.com/your-user-name/init-local-repo (push)

8.4 Deleting a repository on GitHub

We can use gh repo delete to remove a repository from GitHub when it is no longer needed. For example, let’s delete the two repositories we created in the previous examples:

$ gh repo delete init-on-github --yes
$ gh repo delete init-local-repo --yes

The --yes option skips the confirmation prompt. Use this command with care, as deleting a repository can permanently remove its contents and associated data.

Deleting a repository from GitHub does not delete any local clones. We can remove these separately:

$ cd
$ rm -rf init-on-github init-local-repo

If the GitHub CLI reports insufficient permissions to delete the repositories, you may need to run gh auth refresh -s delete_repo and try again.

8.5 Collaborating on GitHub

GitHub provides several features that facilitate collaboration on a project. Here, we will introduce three of these features: issues, pull requests, and forks.

Issues

GitHub has a built-in issue tracking system that can be used to organize tasks, report bugs, request new features, and discuss work on a project. You can think of GitHub issues as a collaborative to-do list or message board attached to a repository, allowing developers and users to collaborate on the project.

The GitHub CLI provides several commands for managing issues, which we will illustrate in the following example. For a complete list of commands and their options, see the GitHub CLI documentation.

Example

Imagine that we are working on a project with several collaborators. To illustrate how issues can be used to coordinate work, we first create a repository on GitHub and clone it locally:

$ cd ~
$ gh repo create issues-example --public --add-readme --clone
$ cd issues-example

Suppose we want a new feature implemented in the project. We can create an issue describing the proposed feature using gh issue create:

$ gh issue create --title "Implement feature A" --body "Description of the feature to implement."

GitHub assigns each issue a unique number within the repository. We can use gh issue list to list the issues in the repository:

$ gh issue list

ID  TITLE                LABELS  UPDATED           
#1  Implement feature A          about 1 minute ago

The issue has been assigned the number 1. We can inspect its contents by passing this number to gh issue view:

$ gh issue view 1

Other collaborators can now see the issue and discuss the proposed feature. For example, we can add a comment indicating that we will implement the feature:

$ gh issue comment 1 --body "I'll implement this feature."

Once the requested feature has been implemented, we can close the issue using gh issue close:

$ gh issue close 1

Finally, we clean up by deleting the example repository from GitHub and removing the clone:

$ gh repo delete issues-example --yes
$ cd
$ rm -rf issues-example

Pull requests

A pull request is a GitHub feature that allows you to propose merging changes from one branch into another. Before the changes are merged, other collaborators can review the proposed changes, discuss them, and suggest improvements. Pull requests are therefore useful for coordinating and reviewing changes before they are integrated into a project.

The GitHub CLI provides several commands for working with pull requests, including gh pr create to create a pull request, gh pr view to inspect it, and gh pr merge to merge the proposed changes. For example, after developing a new feature in a separate branch, we can create a pull request proposing to merge that branch into main.

Forks

Not everyone has permission to push changes directly to every GitHub repository. This is particularly common in open-source projects, where anyone can contribute, but only certain people have write access to the repository.

GitHub provides a feature called forking to facilitate contributions from people without write access. A fork is a copy of a GitHub repository under your own account that remains linked to the original repository, called the upstream repository. Since you own the fork, you can make changes and push commits to it without affecting the original repository. You can then use a pull request to propose merging your changes into the upstream repository.

Forking is different from cloning a repository. While cloning creates a local copy of a repository on your computer, forking creates a separate repository on GitHub.

Example

Let’s illustrate how forks and pull requests can be used together to contribute to a project where we do not have write access. Imagine that we want to contribute to the git-tutorial-fork-example repository.

First, we use gh repo fork to create a fork under our own GitHub account and clone it to our computer:

$ cd
$ gh repo fork thomas-rasmussen-alt/git-tutorial-fork-example --clone
$ cd git-tutorial-fork-example

Let’s inspect the remotes that have been configured in our local clone:

$ git remote -v
origin    https://github.com/your-user-name/git-tutorial-fork-example.git (fetch)
origin    https://github.com/your-user-name/git-tutorial-fork-example.git (push)
upstream  https://github.com/thomas-rasmussen-alt/git-tutorial-fork-example.git (fetch)
upstream  https://github.com/thomas-rasmussen-alt/git-tutorial-fork-example.git (push)

We can see that two remotes have been configured automatically: origin, which points to our fork, and upstream, which points to the original repository. We can push changes to our fork through origin, but we do not have permission to push changes directly to the upstream repository.

Next, we create a feature branch, implement a change, and push the new branch to our fork:

$ git switch -c implement-feature
$ echo "Implementation of feature" > feature.txt
$ git add feature.txt
$ git commit -m "Implement feature"
$ git push -u origin implement-feature

We can inspect the commit history to see how our feature branch differs from the main branches in our fork and the upstream repository:

$ git log --oneline
d134f37 (HEAD -> implement-feature, origin/implement-feature) Implement feature
dd7b9d9 (origin/main, origin/HEAD, upstream/main, upstream/HEAD) Initial commit

The new commit is now present in our feature branch and has been pushed to our fork on GitHub. However, the upstream repository remains unchanged. We have not added any commits or branches to the upstream repository, and its main branch still points to the original commit. Our changes exist only in our local clone and our fork.

We can now create a pull request proposing that our changes be merged into the main branch of the upstream repository:

$ gh pr create --base main --title "Implement feature" --body "Implementation of a new feature"

Here, --base main specifies that we want to merge our changes into the main branch of the upstream repository. Since we are currently on the implement-feature branch, the GitHub CLI automatically uses this branch from our fork as the source of the proposed changes. The pull request is created in the upstream repository, which was configured as the default repository when we created the fork.

The command creates the pull request on GitHub and displays its URL. We can inspect the pull request using gh pr view:

$ gh pr view

gh pr view displays the pull request associated with our current branch in the upstream repository.

The maintainers of the upstream repository can now review and discuss the proposed changes before deciding whether to merge them. We will not illustrate the review and merging process here.

Finally, we can clean up by closing the pull request, deleting our fork, and removing the local clone. Replace <number> with the pull request number. Although we do not have write access to the upstream repository, we are allowed to close the pull request because we created it:

$ gh pr close <number> --repo thomas-rasmussen-alt/git-tutorial-fork-example
$ gh repo delete your-user-name/git-tutorial-fork-example --yes
$ cd
$ rm -rf git-tutorial-fork-example

8.6 GitHub Pages

GitHub Pages is a static site hosting service that can publish HTML, CSS, and JavaScript files from a GitHub repository as a website. It is relatively easy to set up and can be used for a variety of purposes. Common uses include:

  • Documentation

  • Personal websites

  • Blogs

  • Resumes

For example, the tutorial you are reading is hosted using GitHub Pages and is published from the main branch of its GitHub repository. Whenever changes are pushed to main, the website is automatically updated.

Explaining how to set up GitHub Pages is outside the scope of this tutorial. For more information, see the official documentation.

8.7 A note on licences

When making a Git repository publicly available on GitHub, it is important to consider how others are allowed to use its contents. A licence specifies what others may do with your code. Although you are not required to include one, without a licence, default copyright laws generally restrict others from copying, modifying, or distributing your work.

A common choice for open-source projects is the MIT licence. This is a short, permissive software licence that allows others to use, modify, and distribute your code, provided they retain the original copyright and licence notices. It also includes disclaimers of warranty and liability. If you want to learn more about licences, the following resources may be useful:

https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository

https://opensource.guide/legal/#which-open-source-license-is-appropriate-for-my-project

https://choosealicense.com

https://www.tldrlegal.com

8.8 Summary

In this chapter, we have introduced GitHub as a platform for hosting Git repositories and facilitating collaboration. We have learned how to create and manage repositories on GitHub, use issues to organize work, and use forks and pull requests to contribute to projects. We have also briefly introduced GitHub Pages and discussed the importance of licensing when sharing code.

Throughout the chapter, we have used the GitHub CLI to interact with GitHub from the command line. However, the web user interface may be more convenient for some tasks, particularly when browsing repositories and reviewing changes. Both interfaces have advantages, and the choice depends on the task and personal preferences.

8.9 Exercises

The exercises in this chapter require you to work more independently than in previous chapters. Some tasks involve using GitHub CLI commands or options that have not been introduced in the chapter. Rather than providing detailed instructions for every step, we encourage you to consult the GitHub CLI documentation and work out how to complete these tasks independently. Learning how to find information and solve unfamiliar problems is an important skill when working with Git and GitHub.

Exercise 1 - Managing a GitHub repository

In this exercise, we will practice using the GitHub CLI to manage a repository on GitHub. We will create a repository, use an issue to organize work, and create a pull request to merge changes from a feature branch into the main branch.

Step 1 - Create a repository.

Create a public repository named my-repo directly on GitHub, with an initial commit that adds a README and an MIT licence.

TipHint

Use gh repo create --help to explore the available options for creating a repository.

NoteSolution 
$ gh repo create my-repo --public --add-readme --license=mit

Step 2 - Inspect the repository.

Use the GitHub CLI to open the repository in your web browser. Inspect its contents, including the README and licence files.

TipHint

Look at the documentation for gh repo view to find an option for opening the repository in your browser.

NoteSolution 
$ gh repo view my-repo --web

Step 3 - Clone the repository.

Clone the repository to your computer and navigate into its directory. Then inspect the commit history and list the files.

NoteSolution 
$ cd
$ git clone https://github.com/your-user-name/my-repo.git
$ cd my-repo
$ git log --oneline
a4b8f65 (HEAD -> main, origin/main, origin/HEAD) Initial commit
$ ls
LICENSE  README.md

Replace your-user-name with your GitHub username.

Step 4 - Create an issue.

Create an issue requesting a new file named feature_A.txt that contains a short description of feature A. Give the issue the title Implement feature A, assign it to yourself, and add the enhancement label.

TipHint

Use gh issue create. Refer to its documentation to find the options for assigning issues and adding labels.

NoteSolution 
$ gh issue create --title "Implement feature A" --body "Add a file named feature_A.txt describing feature A." --assignee "@me" --label "enhancement"

Step 5 - Implement the feature.

Implement the feature requested in Step 4 by creating a new branch named implement-feature-A and adding a file named feature_A.txt. Use the following commands to create the branch, add the file, and commit the changes:

$ git switch -c implement-feature-A
$ echo "Implementation of feature A" > feature_A.txt
$ git add feature_A.txt
$ git commit -m "Implement feature A"

Now push the new branch to the GitHub repository.

NoteSolution 
$ git push -u origin implement-feature-A

Step 6 - Create a pull request.

Create a pull request using the GitHub CLI to propose merging implement-feature-A into main. Give the pull request an appropriate title and description.

TipHint

Use gh pr create. You can find its documentation using gh pr create --help.

NoteSolution 
$ gh pr create --base main --title "Implement feature A" --body "Implements the change requested in issue #1."

Step 7 - Inspect and merge the pull request.

Inspect the pull request using the GitHub CLI. Then merge the pull request into main using a merge commit, and delete the feature branch. Finally, close the issue created in Step 4, specifying that it has been completed.

TipHint

Use gh pr view to inspect the pull request and gh pr merge to merge it. Consult the documentation to identify the options for using a merge commit and deleting the feature branch.

NoteSolution 
$ gh pr view
$ gh pr merge --merge --delete-branch
$ gh issue close 1 --reason completed

Step 8 - Inspect closed issues.

Use gh issue list to verify that the issue has been closed. By default, this command lists only open issues. Consult the GitHub CLI documentation to find an option that allows you to list closed issues instead.

NoteSolution 
$ gh issue list --state closed

Step 9 - Clean up.

Delete the GitHub repository and its local clone.

NoteSolution 
$ gh repo delete my-repo --yes
$ cd
$ rm -rf my-repo

If the GitHub CLI reports insufficient permissions to delete the repository, run gh auth refresh -s delete_repo and try again.

Exercise 2 - Contributing to a project using a fork

In this exercise, we will practice contributing to a GitHub repository where we do not have write access. We will use the same example repository introduced earlier in this chapter. If you followed the example earlier in this chapter, make sure you have deleted the fork and local clone created in that example before starting this exercise.

Step 1 - Fork and clone the repository.

Create a fork of thomas-rasmussen-alt/git-tutorial-fork-example under your GitHub account, clone it to your computer using the GitHub CLI, and navigate into the clone.

NoteSolution 
$ cd
$ gh repo fork thomas-rasmussen-alt/git-tutorial-fork-example --clone
$ cd git-tutorial-fork-example

Step 2 - Implement a change.

Create a new branch named exercise-change. In this branch, create a file named exercise.txt, add some text to it, and commit the change.

NoteSolution 
$ git switch -c exercise-change
$ echo "A contribution to the project" > exercise.txt
$ git add exercise.txt
$ git commit -m "Add exercise contribution"

Step 3 - Push changes to the fork.

Push the new branch to your fork on GitHub.

NoteSolution 
$ git push -u origin exercise-change

Step 4 - Create a pull request.

Create a pull request proposing to merge the changes from your feature branch into main in the upstream repository. Give the pull request an appropriate title and description.

NoteSolution 
$ gh pr create --base main --title "Add exercise contribution" --body "A contribution made as part of the Git tutorial exercise."

Step 5 - Inspect the pull request.

Use the GitHub CLI to inspect the pull request you just created. Verify that it proposes merging changes from your feature branch into the main branch of the upstream repository.

NoteSolution 
$ gh pr view

Step 6 - Clean up.

Close the pull request without merging it, delete your fork on GitHub, and remove the local clone.

NoteSolution 
$ gh pr close <number>
$ cd
$ gh repo delete your-user-name/git-tutorial-fork-example --yes
$ rm -rf git-tutorial-fork-example

Replace <number> with the number of the pull request, and replace your-user-name with your GitHub username when deleting the fork.

Exercise 3 (optional) - Explore the GitHub web interface

Throughout this chapter, we have used the GitHub CLI to interact with GitHub. However, as previously mentioned, the web interface is often more convenient for some tasks. It is therefore worth spending some time becoming familiar with it.

Go to https://github.com and explore how to use the web interface to perform some of the operations introduced in this chapter. For example, try finding out how to create repositories, manage issues, and create and review pull requests using the web interface instead of the GitHub CLI.

There are no specific tasks to complete in this exercise. The goal is to become familiar with how the operations introduced in this chapter can also be performed through the GitHub web interface.
