2  Getting started

In this chapter we will do basic configuration of Git, and introduce the most basic git commands to create a Git repository, and stage and commit changes. We will also explain how to ignore certain files, and how to access documentation for Git commands.

We will assume the reader is familiar with working from the terminal using Git Bash. If you are not, start by reading Appendix A.

2.1 Basic configuration of Git

First and foremost, there are some basic configurations of Git that should be done using the git config command. Here, we will simply show which commands to use. For a more in-depth introduction to configuration of Git see Appendix B

Change the core editor

Git for Windows comes with a Vim installation, and Git uses Vim as the default text editor that the user will be prompted to use for writing text. If you do not already know what Vim is, it is most certainly not an appropriate text editor for you to use. The only thing we will explain about Vim, is how to properly exit it if you open it by accident: type <Esc>:q!<Enter>. Pressing <Esc> is to make sure you are in normal mode, and :q! is a command to quit Vim and discard any unsaved changes.

This tutorial is aimed at Windows users, so a sensible text editor to use could be Notepad. To change the default text editor to Notepad, which is pre-installed on Windows systems, write the following command:

$ git config set --global core.editor notepad

This tells Git to use Notepad as a text editor in all your Git repositories. Git should be able locate your Notepad executable. If not, specify the full path to the Notepad, which is typically C:/Windows/System32/notepad.ext:

$ git config set --global core.editor "C:/Windows/System32/notepad.exe"

Identify yourself

Another thing you should configure is your name and email, which is included in commits you make. You can specify this with the following commands:

$ git config set --global user.name "Your name"
$ git config set --global user.email "your@email.com"

2.2 Initializing and cloning Git repositories

To start using Git, you need to either initialize a new Git repository, or clone an existing one.

Initialize a Git repository

To initialize a Git repository in a directory, use git init:

username@computer-id MINGW64 ~
$ mkdir ~/example-getting-started
$ cd ~/example-getting-started
username@computer-id MINGW64 ~/example-getting-started
$ git init
Initialized empty Git repository in C:/Users//example-getting-started/.git/
username@computer-id MINGW64 ~/example-getting-started (main)
$ ls -A
.git/

As you can see from the output of git init, this creates an empty Git repository in a subdirectory named .git. Furthermore, the prompt now ends with (main). This is Git Bash telling us that we are in a Git repository and on the main branch. Depending on your Git installation, the name might be master instead of main. We will talk more about branches in Chapter 5.

Clone an existing Git repository

To clone an existing Git repository use git clone. This makes a copy of the repository in your current working directory. You can clone a repository from another directory on your computer, from a directory on a network drive, or from an url. The source code for this tutorial is available on Github. You could make a clone of the repository in your home directory by using the commands:

$ cd  ~
$ git clone "https://github.com/thomas-rasmussen/git-tutorial.git"

This will create a directory named git-toturial, and copy the repository there.

2.3 States of files

Before we introduce the commands you use add changes to the staging area, and commit changes to a repository, we need to introduce some terminology regarding the different states files can be in.

Each file in a Git repository can is either tracked or untracked. Tracked files are files that Git know about, i.e. files that are have previously been committed to your your repository or files that are in the staging area. Untracked files is everything else.

Additionally, tracked files in the working directory are further categorized as either unmodified, modified, and staged. A file is unmodified if no changes has been made to it. A file is modified if changes has been made to it, and a file is staged if changes to the file has been added to the staging area.

When you edit a tracked file, Git sees it as modified since it is different from the last snapshot. You can then stage files for the next commit, and finally commit them. When you commit the file, the file goes back to being viewed as unmodified. You then then continue editing, staging and commiting files, and thus the cycle repeats.

2.4 Checking the state of files

The main command to check the states of files is git status. If we run this command in the empty example-getting-started repository we created earlier we we see something like:

username@computer-id MINGW64 ~/example-getting-started (main)
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

We are informed that there are no commits in the repository, and that there is nothing to commit at this point, e.g. all the files in the repository are unmodified. Finally, we are informed that we can create files and use git add to track them.

2.5 Adding changes to the staging area

To add changes to the staging area, we can use the git add command, as Git also informed informed us in the example above. This will update the staging area using the current contents of the working tree, which can include updating files that are already in the staging area, include new files, or remove files that are no longer in the working tree. The staging area holds a snapshot of the content that we want to include in our next commit.

Continuing our example, we first create a file in the working tree:

$ echo "Contents of file1.txt" > file1.txt

We now have an untracked file in our repository. If we run git status again we see the following:

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add ..." to include in what will be committed)
        file1.txt

nothing added to commit but untracked files present (use "git add" to track)

Git is also noting that file1.txt is untracked.

Now we add file1.txt to the staging area:

$ git add file1.txt
warning: in the working copy of 'file1.txt', LF will be replaced by CRLF the next time Git touches it

If we wanted to add multiple files to the staging area at once we could do so using e.g. git add file1.txt file2.txt or git add ., where git add . adds all files in the working tree to the staging area.

When we add the file to the repository we get a warning that is quite cryptic at this point. The warning has to do with how line endings are handled in the repository, and is caused by the fact that we created the contents using a command in Git Bash instead of making it in e.g. Notepad manually. We will not go into details with why this happens, but rest assured that everything is fine and the warning can be ignored. (TODO: is it worth it to explain this in more details?).

file1.txt has now been added to the staging area, and is no longer an untracked file, but instead a staged file. At this point let’s use git status again:

$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached ..." to unstage)
        new file:   file1.txt

We are now informed that file1.txt has been added to the staging area, and will be included in the next commit. Git also helpfully informs us, that we can unstage file by using git rm --cached ....

2.6 Viewing differences

As we saw in the last section, we can stage files using git add. But before actually committing them, we might be interested in seeing exactly what changes we are commiting. We can do this using git diff. Continuing the example, lets try to use git diff. By default, git diff shows differences between the working tree and the last commit. What we want to see is the differences between the staging area and the last commit, and we can do this using the --cached flag:

$ git diff --cached
diff --git a/file1.txt b/file1.txt
new file mode 100644
index 0000000..85e8799
--- /dev/null
+++ b/file1.txt
@@ -0,0 +1 @@
+Contents of file1.txt

The output is quite complex, but we can see that the green line indicates the lines that will be added. We will not talk more about git diff at this point, but will go in-depth with that particular command in Chapter 9.

2.7 Committing files to the repository

We have now seen how to add changes to the staging area using git add and how to inspect the added changes using git diff. To commit changes in the staging area to the repository, use git commit. This uses the current content of the staging areas to create a new commit to the repository. Continuing our example:

$ git commit

When using this command, Git will open a text editor for you to enter a commit message. After writing the message, save the file, and exit the editor. This is why it is important to configure what text editor Git uses, as explained earlier.

You can also use the -m flag to write a commit message directly:

$ git commit -m"Commit message"

After making the commit, git commit outputs something like the following in the terminal:

[main (root-commit) b68a80a] Commit message
 1 file changed, 1 insertion(+)
 create mode 100644 file1.txt

This is very technical, but we can discern that the commit included changes to file1.txt.

After committing file1.txt to the repository, file1.txt goes back to being unmodified, since the file is now the same as in the repository.

2.8 Viewing the commit log

To view the commit log of a repository use git log. Continuing our example:

username@computer-id MINGW64 ~/example-getting-started (main)
$ git log
commit b68a80aa01df294c1eb6ee43146536b54c1f4b53 (HEAD -> main)
Author: Your Name 
Date:   Fri Oct 16 12:20:47 2026 +0200

    Commit message

The repository only has one commit, and we can see that we are provided with information on the author and date of the commit together with the commit message. We will discuss git log in more details in Chapter 3.

2.9 Ignoring files

It is more common than not, that your repository contains files that you do not want Git to track. For example, you might have a directory with documents related to your project, that you store in your project to make it self-contained, but the documents themselves is not something that you want to version control.

In a Git repository you can make a file called .gitignore, and in this file you can specify files that Git should ignore. Each line in .gitignore specifies a pattern. A .gitignore file could look like this:

.gitignore
# Lines starting with a '#' are comments. # Ignore project description project-description.pdf # Ignore all files ending in ".pdf" or ".docx" in 'doc' subdirectory doc/*.pdf doc/*.docx

It is important that Git only ignores files that are not already tracked.

.gitignore files are important when using Git in a real project but is not something that will pop up more in this tutorial. If you want to know more about how to ignore files when using Git, see ?sec-ignoring-files.

2.10 Accessing manual pages

We will end this chapter with a note on how to access the comprehensive manual help page for any of the Git commands. The manual pages can be accessed in different equivalent ways one of which is:

$ git help <command>

For example, to get the manual page for the git add command run

$ git help add

These manual pages are nice because they can be accessed anywhere, even offline. A short summary on how to use the command can also be printed in the terminal by using the -h option with a git command:

$ git help add -h
usage: git add [] [--] ...

    -n, --[no-]dry-run    dry run
    -v, --[no-]verbose    be verbose

    -i, --[no-]interactive
                          interactive picking
    -p, --[no-]patch      select hunks interactively
    -U, --unified <n>     generate diffs with <n> lines context
    --inter-hunk-context <n>
                          show context between diff hunks up to the specified number of lines
    -e, --[no-]edit       edit current diff and apply
    -f, --[no-]force      allow adding otherwise ignored files
    -u, --[no-]update     update tracked files
    --[no-]renormalize    renormalize EOL of tracked files (implies -u)
    -N, --[no-]intent-to-add
                          record only the fact that the path will be added later
    -A, --[no-]all        add changes from all tracked and untracked files
    --[no-]ignore-removal ignore paths removed in the working tree (same as --no-all)
    --[no-]refresh        don't add, only refresh the index
    --[no-]ignore-errors  just skip files which cannot be added because of errors
    --[no-]ignore-missing check if - even missing - files are ignored in dry run
    --[no-]sparse         allow updating entries outside of the sparse-checkout cone
    --[no-]chmod (+|-)x   override the executable bit of the listed files
    --[no-]pathspec-from-file 
                          read pathspec from file
    --[no-]pathspec-file-nul
                          with --pathspec-from-file, pathspec elements are separated with NUL character

Exercise 1 - Create a new Git repository

NoteExercise

  1. Initialize an empty Git repository in a new subdirectory of your home directory named “ex-init-repo”.

  2. cd into the directory

  3. Create a file (any file will do).

  4. Add the file to the index.

  5. Commit the file to the repository.

TipHint

Look at the example in section ?sec-getting-started-example.

ImportantSolution 
$ cd ~ # Make sure the working directory is set to the home directory
$ mkdir ex-init-repo # Make a new subdirectory
$ cd ex-init-repo # cd to new directory
$ git init # Initialize git repository
$ echo "Some content" > file.txt # Create a file in the directory
$ git add file.txt # Add file to index
$ git commit -m"Commit message" # Commit to repository

Exercise 2 - Using the manual pages

In this exercise we will practice using the manual pages. First lets construct a simple git repository with different files in different states.

$ cd ~
$ mkdir ex-man-pages
$ cd ex-man-pages
$ git init
$ echo "Content of file1" > file1.txt
$ git add file1.txt
$ git commit -m"Add file1.txt"
$ rm file1.txt
$ echo "Content of file2" > file2.txt
$ echo "Content of file3" > file3.txt
$ git add file2.txt

If we run git status on the repository in this state we get the following output in the terminal

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        new file:   file2.txt

Changes not staged for commit:
  (use "git add/rm ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        deleted:    file1.txt

Untracked files:
  (use "git add ..." to include in what will be committed)
        file3.txt

The output is rather verbose, and with more files (which is common) it quickly becomes unnecessarily hard to get an overview. It would be great if we could get the output from git status in a shorter, more condense, format.

  1. Look at the git status command documentation, and find an option that can be used to show the status concisely.
TipHint

You can either look at the “OPTIONS” section of manual page using the git help status, or you can use git status -h to get get a quick overview of how to use the command.

NoteSolution

The option we are looking for is -s.

$ git status -s
 D file1.txt
A  file2.txt
?? file3.txt
  1. Read further into the documentation and find the section explaining the notation used in the short short format. You can skim through the documentation if you want to, but you don’t need to use time trying to understand it.
NoteSolution

In this case we need to read a little further in the manual page for git status. The information we are looking for can be found in the “Short Format” subsection of the section “OUTPUT”.

Exercise 4 - Turn an existing directory into a Git repository

Try to make an existing project/folder into a Git repository, and add and commit files to the repository. Consider the following types of files and whether or not it is a good idea to version control them:

  1. Source code

  2. Generated files

  3. Data

  4. Personal IDE config files. for example the content of the hidden folder .Rproj.user for Rstudio users.

At this point you might wonder if it is possible to tell Git to ignore certain files and file types, so that the worktree is not clogged with untracked files. Yes, it most certainly can. We will get back to that later in the tutorial.

Note“Solution”

We will get back to this subject later in the tutorial, but generally speaking you should version control your code, not your output. so:

  1. Definitely yes.

  2. Probably not. You can always generate them from the code. In some cases generated file can take a long time to generate, and are small in size. In that case, it might be convenient to just version control such files if we know we might need to look at different version of the files.

  3. Depends. If the data is generated from your code, then probably not. If it is “raw” data then maybe.

  4. Almost certainly no. Especially not if you are collaborating on a project with other people.
