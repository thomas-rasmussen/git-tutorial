5  Undoing changes

When working with Git, you will inevitably make mistakes or make changes that you later want to undo. For example, you might accidentally stage a file, make unwanted changes to a file, or discover an error in a commit.

Git provides several commands for undoing changes, depending on whether the changes are in the working tree, the staging area, or have already been committed. Some commands allow you to undo changes while preserving your work, whereas others permanently discard changes.

In this chapter, you will learn how to use git commit --amend to modify the current commit, git restore to discard and unstage changes, and git reset to undo commits. You will also learn which operations can permanently discard uncommitted changes.

5.1 Amending the current commit

Common mistakes include forgetting to stage changes before making a commit and making typos in commit messages. You could make an additional commit to include forgotten changes, but this would make the commit history less tidy. Furthermore, an additional commit cannot correct a typo in an earlier commit message. Both problems can be corrected using git commit --amend, which replaces the current commit with a new commit. This allows you to include additional staged changes, update the commit message, or both.

Let’s illustrate this with an example. First, we create a repository, add a file named file1.txt, and commit it:

$ mkdir ~/example01-undoing-changes
$ cd ~/example01-undoing-changes
$ git init
$ echo "Contents" > file1.txt
$ git add file1.txt
$ git commit -m "Add file.txt"
$ git log --oneline
1d38fb6 (HEAD -> main) Add file.txt
$ cat file1.txt
Contents

Now we stage additional changes to file1.txt and use git commit --amend:

$ echo "Updated contents" > file1.txt
$ git add file1.txt
$ git commit --amend -m "Add file1.txt"
$ git log --oneline
32c7f65 (HEAD -> main) Add file1.txt
$ cat file1.txt
Updated contents

Notice that the current commit has been replaced with a new commit with a different commit ID. Here we used the -m option to specify the new commit message directly. If you amend the commit without specifying -m, Git opens a text editor with the existing commit message already filled in. You can then change it if you want to.

It’s important to understand that amending a commit rewrites the history of your repository, which can cause problems when the commit has already been shared with others. We will explain when this is problematic in Chapter 11.

5.2 Restoring the working tree and staging area

The git restore <file> command can be used to restore files in the working tree or staging area using contents from a restore source. We can use this command to undo changes we have made in the working tree, unstage changes from the staging area, and also restore earlier versions of files.

Discarding changes in the working tree

By default, git restore <file> restores files in the working tree, which is equivalent to specifying the --worktree option. The default restore source when restoring files in the working tree is the staging area.

Let’s illustrate how we can use git restore <file> to discard changes in the working tree. First, we create a repository containing a single commit that adds a file named file1.txt:

$ mkdir ~/example02-undoing-changes
$ cd ~/example02-undoing-changes
$ git init
$ echo "Contents of first commit" > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"

Next, we modify file1.txt in the working tree but decide that we do not want to keep the changes. We can discard them using git restore file1.txt:

$ echo "Unstaged changes in working tree" >> file1.txt
$ cat file1.txt
Contents of first commit
Unstaged changes in working tree
$ git restore file1.txt
$ cat file1.txt
Contents of first commit

After using git restore file1.txt, the working tree version of file1.txt has been restored using the version from the staging area, which in this example matches the current commit.

Warning: Using git restore to discard changes in the working tree is convenient, but it is also a potentially destructive operation. You might not be able to recover discarded changes.

Unstaging changes

If we use git restore with the --staged option, Git will restore the file in the staging area instead of the working tree. When --staged is used, the default restore source is HEAD, which is equivalent to specifying the option --source=HEAD.

Let’s illustrate this by continuing the previous example. First, we check the status of our repository and then stage some changes to file1.txt:

$ git log --oneline
4827a13 (HEAD -> main) Add file1.txt
$ git status
On branch main
nothing to commit, working tree clean
$ echo "New staged changes" >> file1.txt
$ git add file1.txt
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        modified:   file1.txt

Next, we unstage the changes by replacing the staged version of file1.txt with the version from HEAD:

$ git restore --staged file1.txt
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   file1.txt

no changes added to commit (use "git add" and/or "git commit -a")

Notice that when we run git status with staged changes, Git tells us how to unstage them using git restore --staged <file>.

Restoring a previous version of a file

So far, we have relied on Git’s default restore sources. However, the --source option allows us to specify a different source. We can use this option to restore an earlier version of a file.

Let’s illustrate this by creating a repository containing three committed versions of file1.txt:

$ mkdir ~/example03-undoing-changes
$ cd ~/example03-undoing-changes
$ git init
$ echo "Contents in first commit" > file1.txt
$ git add file1.txt
$ git commit -m "First commit"
$ echo "Contents in second commit" > file1.txt
$ git add file1.txt
$ git commit -m "Second commit"
$ echo "Contents in third commit" > file1.txt
$ git add file1.txt
$ git commit -m "Third commit"

We can restore the version of file1.txt from the first commit by identifying its commit ID and specifying it using the --source option with git restore:

$ git log --oneline
926eed2 (HEAD -> main) Third commit
98ea03d Second commit
6910c18 First commit
$ cat file1.txt
Contents in third commit
$ git restore --source=6910c18 file1.txt
$ cat file1.txt
Contents in first commit
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   file1.txt

no changes added to commit (use "git add" and/or "git commit -a")

We could stage this change using git add. Alternatively, we can restore the earlier version directly into the staging area using --staged:

$ git restore --staged --source=6910c18 file1.txt
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        modified:   file1.txt

The commit history remains unchanged, and the restored version is now staged and ready to commit.

Restoring files in both the working tree and staging area

So far, we have seen how to restore files in the working tree or staging area separately, using either the default behaviour or the --worktree and --staged options. We can also combine these options to restore a file in both the working tree and staging area simultaneously.

Continuing the previous example, we can restore file1.txt to the version from the third commit in both the working tree and staging area:

$ git restore --worktree --staged --source=HEAD file1.txt
$ cat file1.txt
Contents in third commit
$ git status
On branch main
nothing to commit, working tree clean

As demonstrated here, using the --worktree and --staged options allows us to restore files in the working tree and staging area either separately or simultaneously.

5.3 Undoing commits

We can use git reset <commit> to change the current commit to the specified commit. By default, git reset uses the --mixed option, which leaves the working tree unchanged and resets the staging area to match the specified commit.

Let’s illustrate this with an example. First, we create a repository with two commits of a file named file1.txt:

$ mkdir ~/example04-undoing-changes
$ cd ~/example04-undoing-changes
$ git init
$ echo "Contents of first commit" > file1.txt
$ git add file1.txt
$ git commit -m "First commit"
$ echo "Contents of second commit" > file1.txt
$ git add file1.txt
$ git commit -m "Second commit"
$ git status
On branch main
nothing to commit, working tree clean

$ git log --oneline
0411b50 (HEAD -> main) Second commit
f1aedfd First commit

Now we use git reset HEAD^ to change the current commit to the parent of HEAD, which is the first commit in our example:

$ git reset HEAD^
Unstaged changes after reset:
M       file1.txt
$ git log --oneline
f1aedfd (HEAD -> main) First commit
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   file1.txt

no changes added to commit (use "git add" and/or "git commit -a")

$ cat file1.txt
Contents of second commit

The first commit is now the current commit, and the second commit no longer appears in the commit history. However, the working tree has been preserved and still contains the changes introduced by the second commit.

We can therefore use git reset to undo one or more commits without necessarily discarding their changes.

As explained earlier, git reset uses the --mixed option by default, preserving the working tree. You can also use --soft to preserve both the working tree and the staging area. Finally, --hard resets both the working tree and staging area to match the specified commit. This discards changes to tracked files that differ from the specified commit, including any uncommitted changes. Therefore, --hard should be used with care.

The following table summarizes how the different modes of git reset affect the working tree and staging area:

Mode Working tree Staging area
--soft Unchanged Unchanged
--mixed (default) Unchanged Reset to target commit
--hard Reset to target commit Reset to target commit

The choice of mode therefore determines whether the working tree and staging area are preserved or reset to match the specified commit.

5.4 Summary

In this chapter, you learned how to undo changes and correct mistakes in a Git repository.

  • git commit --amend allows you to modify the current commit, for example to correct its commit message or include additional changes.

  • git restore allows you to discard changes in the working tree or unstage changes without discarding them. You can also use it to restore earlier versions of files.

  • git reset allows you to make an earlier commit the current commit. Depending on the options used, you can either preserve or discard the changes introduced by subsequent commits.

Some of these operations can permanently discard changes, while others modify the commit history. You should therefore use them carefully, particularly when discarding uncommitted changes or rewriting commits that have already been shared with others.

Exercise 1 - Amending commits

In this exercise, you will practice amending commits. Run the following commands to set up a repository with a single commit of a file named file1.txt:

$ mkdir ~/ex01-undoing-changes
$ cd ~/ex01-undoing-changes
$ git init
$ echo "Draft of contents" > file1.txt
$ git add file1.txt
$ git commit -m "Add file1.txt"

1. Update file1.txt by amending the commit.

Change the line in file1.txt from Draft of contents to Contents, stage the changes, and amend the changes to the existing commit. Keep the existing commit message. Run git log --oneline before and after amending the commit, and explain what has changed and why.

NoteSolution 
$ echo "Contents" > file1.txt
$ git add file1.txt
$ git log --oneline
86b78d9 (HEAD -> main) Add file1.txt
$ git commit --amend -m "Add file1.txt"
$ git log --oneline
8d1a459 (HEAD -> main) Add file1.txt

The commit ID has changed because amending the commit replaces it with a new commit.

2. Reusing the commit message.

Run the following commands to stage additional changes to file1.txt that we want to include by amending the commit again:

$ echo "More content" >> file1.txt
$ git add file1.txt

In Step 1 we had to either use the -m option to specify the new commit message, or confirm the commit message in a text editor. However, opening a text editor or using the -m option is inconvenient when we want to retain the existing commit message. Consult the git commit documentation to find an option that allows us to reuse the existing commit message without launching a text editor, and use this option to amend the commit with the new changes.

TipHint 1

The git commit documentation is extensive, including many options. Press <Ctrl> + f in your browser and search for --amend to see if the option we are looking for is described near the use of --amend in the documentation.

TipHint 2

The option we are looking for is --no-edit.

NoteSolution 
$ git commit --amend --no-edit

Exercise 2 - Restoring files

In this exercise, you will practice restoring files. First, use the following commands to set up a repository with two commits of a file named file.txt:

$ mkdir ~/ex02-undoing-changes
$ cd ~/ex02-undoing-changes
$ git init
$ echo "Contents in first commit" > file.txt
$ git add file.txt
$ git commit -m "First commit"
$ echo "Contents in second commit" > file.txt
$ git add file.txt
$ git commit -m "Second commit"

1. Discard unstaged changes.

Make a change in file.txt in the working tree, and then use git restore to discard it. Consider what options you need to specify, if any. Explain what restore source we need to use to discard the unstaged change.

NoteSolution

We want to restore file.txt in the working tree using either HEAD or the staging area as the restore source. Both sources contain the version of file.txt with the line Contents in second commit. By default, git restore restores the working tree, which is equivalent to specifying --worktree. When restoring the working tree, Git’s default restore source is the staging area, which is also what we want. So we can simply use git restore file.txt to discard the change in the working tree:

$ echo "Add change in working tree" >> file.txt
$ cat file.txt
Contents in second commit
Add change in working tree
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   file.txt

no changes added to commit (use "git add" and/or "git commit -a")

$ git restore file.txt
$ cat file.txt
Contents in second commit
$ git status
On branch main
nothing to commit, working tree clean

2. Unstage changes.

Make another change to file.txt and stage it. Use git restore to unstage the change. Consider what options you need to specify, if any. Explain what restore source we need to use to unstage the change.

NoteSolution

To unstage changes, we restore the staging area using the version of the file from the current commit. We can restore files in the staging area by using the --staged option. By default, Git uses the contents of the current commit as the restore source:

$ echo "Staged change" >> file.txt
$ git add file.txt
$ cat file.txt
Contents in second commit
Staged change

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        modified:   file.txt

$ git restore --staged file.txt
$ cat file.txt
Contents in second commit
Staged change
$ git status
On branch main
Changes not staged for commit:
  (use "git add ..." to update what will be committed)
  (use "git restore ..." to discard changes in working directory)
        modified:   file.txt

no changes added to commit (use "git add" and/or "git commit -a")

3. Restore an earlier version of a file.

Use git restore to restore file.txt in both the working tree and the staging area to the version in the first commit. Before executing the command, consider what will happen to the unstaged changes from Step 2.

NoteSolution 
$ git restore --worktree --staged --source=HEAD^ file.txt

The unstaged changes in the working tree will be discarded.

4. Inspect the repository.

Use git log --oneline and git status to inspect the state of the repository. Use cat to see the contents of file.txt. Before doing so, predict the output. Also run git diff --staged and explain the output.

NoteSolution 
$ git log --oneline
0d2e21e (HEAD -> main) Second commit
28f4517 First commit
$ cat file.txt
Contents in first commit
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged ..." to unstage)
        modified:   file.txt
$ git diff --staged
diff --git a/file.txt b/file.txt
index 24710b0..ce44375 100644
--- a/file.txt
+++ b/file.txt
@@ -1 +1 @@
-Contents in second commit
+Contents in first commit

We have restored the first version of file.txt in both the working tree and the staging area, but we have not altered the commit history, so git log --oneline will still show two commits in the repository.

Both the working tree and staging area now contain the version of file.txt from the first commit, with the line Contents in first commit.

The git diff --staged output shows the differences between the current commit and the staging area. Although we restored an earlier version of file.txt, the current commit has not changed. Therefore, Git compares the version of file.txt from the second commit with the restored version in the staging area. This explains why Contents in second commit is shown as a removed line and Contents in first commit as an added line.

Exercise 3 - Undoing commits

In this exercise, you will practice undoing a commit. Start by setting up a repository with two commits of a file named file.txt:

$ mkdir ~/ex03-undoing-changes
$ cd ~/ex03-undoing-changes
$ git init
$ echo "Original contents" > file.txt
$ git add file.txt
$ git commit -m "Add file.txt"
$ echo "Experimental changes" > file.txt
$ git add file.txt
$ git commit -m "Make experimental changes to file.txt"

The repository now contains two commits, the second of which introduces experimental changes to file.txt.

1. Undo experimental changes.

Imagine that we regret the experimental changes introduced by the second commit and want to discard both the commit and its changes. Use git reset to do this. Consider which mode is appropriate and explain your choice.

NoteSolution

We can use git reset --hard HEAD^ to make the first commit the current commit and reset both the working tree and staging area to match it. This discards the experimental changes introduced by the second commit:

$ git reset --hard HEAD^

2. Inspect the repository.

After undoing the second commit in the first step, inspect the repository using git log --oneline and git status, and use cat to print the contents of file.txt. Explain what you expect to see before running the commands.

NoteSolution

We have made the first commit the current commit and reset both the working tree and staging area to match it. We expect git log --oneline to show only the first commit and the working tree and staging area to match that commit. We also expect the contents of file.txt to be the line Original contents.

$ git log --oneline
aa35b38 (HEAD -> main) Add file.txt
$ git status
On branch main
nothing to commit, working tree clean

$ cat file.txt
Original contents
